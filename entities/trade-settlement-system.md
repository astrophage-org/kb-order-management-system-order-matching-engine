# Trade Settlement System (TSS)

The **Trade Settlement System (TSS)** is a high-throughput, asynchronous, event-driven post-trade processing engine within the Nexus Trading Exchange (NTE) ecosystem. Positioned completely outside the critical low-latency path of the [[entities/matching-engine]], the TSS decouples execution from administrative, regulatory, and clearing overheads. It consumes execution reports from the `nte.trades.matched` stream and coordinates down-stream post-trade lifecycles, ensuring financial integrity without degrading the microsecond performance of the trading core.

---

## ## Responsibilities

The TSS orchestrates all post-trade states and ledger changes. Its core duties are categorized below:

*   **Ingestion & Deserialization:** Subscribes to the `nte.trades.matched` Kafka topic, processing incoming [[entities/trade-execution-model]] payloads under strict FIFO delivery constraints per partition.
*   **Post-Trade Margin Verification:** Re-evaluates portfolio positions and margin requirements for both counterparties immediately following execution. Unlike pre-trade risk checks, post-trade verification calculates maintenance margin, collateral haircuts, and triggers immediate margin calls or liquidations if a trader falls below maintenance thresholds.
*   **Clearinghouse Routing & Netting:** Translates execution reports into clearing-ready messages (e.g., FIX-over-SWIFT or ISO 20022 formats) and routes them to central clearinghouses (such as NSCC, DTCC, or internal clearing books) for bilateral or multilateral netting.
*   **Custody Balance Updates:** Updates the digital or traditional custody ledger to reflect changes in asset ownership. It manages the lifecycle of the exchange's ledger: locking assets in escrow, settling trades, and releasing funds.
*   **Idempotency & Deduplication:** Guarantees exactly-once processing using the immutable `trade_id` generated by the [[entities/order-book]]. It prevents double-clearing and duplicate settlement of trades during engine failovers or Kafka consumer offset resets.

---

## ## Dependencies

The TSS acts as a bridge between the core order-matching system and external financial infrastructures. Its execution relies on the following key upstream components:

*   **[[concepts/kafka-integration]] (Upstream Data Source):** Consumes from the high-throughput, symbol-keyed `nte.trades.matched` stream. It depends on `kafka.producer_acks = "all"` to ensure that every trade ingested has been durably persisted to the distributed commit log.
*   **[[entities/trade-execution-model]] (Data Contract):** Depends on the immutable schema of the executed trade (containing `trade_id`, `price`, `quantity`, `buyer_id`, `seller_id`, and `exchange_id`) to orchestrate settlement.
*   **External Clearinghouse Gateways:** Integrates with external APIs and Swift networks to route settlement instructions to clearing entities.
*   **Custody Ledger/Database:** Interacts with a stateful, ACID-compliant double-entry ledger database containing the cash and asset balances of all market participants.

## Architectural Position & Event-Driven Topology

To protect the [[summaries/order-matching-engine]] from execution jitter, the clearing and settlement process is isolated from the order-matching cycle. The TSS operates downstream of the OME's egress layer, utilizing a decoupled, pull-based architecture.

```
┌────────────────────────────────────────────────────────┐
│             NTE Order Matching Engine (OME)            │
│  - Ingests orders via [[entities/matching-engine]]     │
│  - Executes matches in memory on the [[entities/order-book]] │
└──────────────────────────┬─────────────────────────────┘
                           │
                           │ Writes trade execution reports
                           ▼
 ┌──────────────────────────────────────────────────────┐
 │ Kafka Log: nte.trades.matched                        │
 │ - Partitioned deterministically by asset symbol      │
 └─────────────────────────┬────────────────────────────┘
                           │
                           │ Consumes asynchronously (Pull model)
                           ▼
┌────────────────────────────────────────────────────────┐
│             Trade Settlement System (TSS)              │
│                                                        │
│  ┌────────────────────────┐   ┌─────────────────────┐  │
│  │  Consumer / Parser     │──>│  Margin Engine      │  │
│  └────────────────────────┘   └──────────┬──────────┘  │
│                                          │             │
│                                          ▼             │
│  ┌────────────────────────┐   ┌─────────────────────┐  │
│  │  Clearinghouse Router  │<──│  Custody Ledger     │  │
│  └──────────┬─────────────┘   └─────────────────────┘  │
└─────────────┼──────────────────────────────────────────┘
              │

  [ External Clearing / Custody Network ] (DTCC, ISO 20022, etc.)
```

## Core Engine Subsystems

### 1. Post-Trade Margin Verification
While basic balance pre-checks prevent initial over-leverage at the [[entities/market-data-gateway]] layer, market volatility and concurrent executions require continuous post-trade validation. The TSS Margin Verification engine:
*   Pulls current mark-to-market prices from the [[entities/market-data-gateway]]'s L2 snapshots.
*   Applies asset-specific haircuts (valuation discounts) to resting collateral.
*   Recalculates the **Maintenance Margin Ratio (MMR)** for both the `BuyerID` and `SellerID` associated with the trade.
*   If a portfolio's equity drops below the MMR, the engine marks the account for liquidation and dispatches a prioritized liquidation order back to the inbound matching queue via the [[entities/matching-engine]].

### 2. Clearinghouse Routing & Netting
For institutional compliance, trades must be cleared and affirmed. The clearing module:
*   Translates trade models into standard protocols (e.g., FIX TradeCaptureReport messages).
*   Coordinates with central counterparties (CCPs).
*   Applies **Continuous Netting**: rather than settling 10,000 individual trades in `BTC/USD`, the clearinghouse router aggregates buy and sell executions per participant over a settlement window, yielding a single net payment or delivery instruction per asset.

### 3. Custody & Ledger Management
The double-entry ledger maintains strict transactional guarantees (ACID). To prevent race conditions during balance settlement, the TSS employs a two-phase state machine:

```
          ┌─────────────┐
          │   PENDING   │  <-- Trade ingested from Kafka; balances locked in escrow.
          └──────┬──────┘
                 │
        ┌────────┴────────┐
        ▼                 ▼
 ┌───────────┐     ┌───────────┐
 │  SETTLED  │     │  FAILED   │ <-- Margin or routing failure;
 └───────────┘     └───────────┘     escrow reversed.
 (Asset ownership transferred)
```

1.  **Pending / Escrow:** Balances corresponding to the traded asset (or quote currency) are transitioned into a `LOCKED_PENDING_SETTLEMENT` status.
2.  **Settle:** Once the clearinghouse affirms the transaction, balances are updated simultaneously. If clearing fails or a margin breach is determined, the locked funds are rolled back, and the trade status is set to `FAILED`.

## Idempotency and Crash Recovery

Because the OME can recover state via event sourcing—replaying past transactions from the immutable Kafka log as detailed in [[concepts/crash-recovery-durability]]—the TSS must handle duplicate messages gracefully to prevent double-clearing.

*   **Deduplication Storage:** The TSS stores processed `trade_id` keys in a high-performance, distributed key-value store (e.g., Redis or Cassandra) with a retention period matching the maximum settlement cycle (e.g., T+2 days).
*   **Offset Tracking:** The TSS maintains its own persistent consumer offset tracking separate from other downstream systems, such as the [[entities/compliance-surveillance-monitor]]. If the TSS crashes, it resumes consumption from its last committed offset, scanning the deduplication store for any duplicate `trade_id`s that might have been re-delivered during consumer group rebalances.
*   **Graceful Degenerate Execution:** In the event of ledger connectivity loss, the TSS pauses the Kafka consumer partition, preventing offsets from advancing. This isolates post-trade issues to the settlement queue without blocking matching operations on the [[entities/order-book]].
