# Trade Execution Model

The `TradeExecution` model is the canonical, immutable data structure representing a finalized match within the Nexus Trading Exchange (NTE). Once an incoming order crosses the spread in an [[entities/order-book]] and successfully matches against resting limit liquidity, a trade is compiled, recorded, and streamed to downstream nodes. 

This model serves as the single source of truth for post-trade financial operations and compliance verification. To guarantee auditability, this structure is strictly **write-once, read-many** and cannot be modified once generated by the [[entities/matching-engine]].

---

## Technical Definition

### Go Representation

As defined in `models/trade.go`:

```go
package models

import "time"

// TradeExecution represents a matched trade.
// Used heavily by trade-settlement-system and compliance-surveillance-monitor.
type TradeExecution struct {
	TradeID      string    `json:"trade_id"`
	Symbol       string    `json:"symbol"`
	Price        float64   `json:"price"`
	Quantity     float64   `json:"quantity"`
	BuyerID      string    `json:"buyer_id"`
	SellerID     string    `json:"seller_id"`
	BuyOrderID   string    `json:"buy_order_id"`
	SellOrderID  string    `json:"sell_order_id"`
	ExecutedAt   time.Time `json:"executed_at"`
	ExchangeID   string    `json:"exchange_id"`
	MatchPhase   string    `json:"match_phase"` // e.g., "CONTINUOUS", "AUCTION"
}
```

### JSON Schema Attributes

| Field Name | Data Type | Description |
| :--- | :--- | :--- |
| `trade_id` | `string` | Universally unique identifier (UUIDv4) generated at the microsecond of match execution. |
| `symbol` | `string` | Financial instrument symbol (e.g., `BTC/USD`) acting as the partition key. |
| `price` | `float64` | The clearing price of the match, determined by the resting limit order price. |
| `quantity` | `float64` | The volume executed in this match. For [[concepts/iceberg-order-engine]], this is restricted to the current visible slice size. |
| `buyer_id` | `string` | Client identification key of the liquidity-taking or liquidity-providing buyer. |
| `seller_id` | `string` | Client identification key of the liquidity-taking or liquidity-providing seller. |
| `buy_order_id` | `string` | Unique identifier referencing the underlying buy [[entities/order-model]]. |
| `sell_order_id`| `string` | Unique identifier referencing the underlying sell [[entities/order-model]]. |
| `executed_at` | `timestamp`| High-precision UTC timestamp representing when the match priority was committed in memory. |
| `exchange_id` | `string` | Unique identifier of the engine instance that executed the match (e.g., `NTE-PROD-01`). |
| `match_phase` | `string` | The operating state of the order book during execution (e.g., `CONTINUOUS`, `AUCTION`). |

## Responsibilities

* **Immutable Settlement Record:** Provides a finalized execution payload containing cleared price and absolute volume, preventing post-trade state divergence between the in-memory core and physical ledgers.
* **Downstream Streaming Interface:** Formats matched executions into a uniform structure optimized for high-throughput JSON serialization over [[concepts/kafka-integration]].
* **Auditable Lineage Maintenance:** Links executions back to their initiating orders via explicit referencing (`buy_order_id`, `sell_order_id`), allowing compliance engines to reconstruct chronological market states.
* **Latency Tracing Boundary:** Serves as the ultimate endpoint for matching-engine telemetric logging, validating that processing latency stays within microsecond-level limits.

---

## Dependencies

The `TradeExecution` model acts as a boundary-spanning entity, interacting with several core components:

* **[[entities/order-book]] & [[concepts/price-time-priority]]**: The matching logic is the exclusive factory of the `TradeExecution` model. Matches are generated within the localized, single-symbol execution locks of the `OrderBook` when an inbound [[entities/order-model]] crosses the book's current spread.
* **[[concepts/kafka-integration]] (`KafkaPublisher`)**: Downstream transport relies on the outbound publisher to serialize the model into JSON payloads and route them to the `nte.trades.matched` topic. The model's `Symbol` field is utilized as the routing key to enforce chronological partition-ordering.
* **[[entities/trade-settlement-system]] (TSS)**: The post-trade processor consumes these payloads from `nte.trades.matched` to conduct real-time margin adjustments, clearinghouse routing, and asset custody updates.
* **[[entities/compliance-surveillance-monitor]] (CSM)**: The surveillance node monitors the stream to detect illicit patterns (such as wash trading, where `buyer_id == seller_id`, or layering/spoofing attempts).

## Data Flow & Lifecyle

```
   ┌─────────────────────────────────────────────────────────┐
   │ 1. Match Occurs inside [[entities/order-book]]          │
   │    - Matches inbound order against resting book.        │
   │    - Unrolls [[concepts/iceberg-order-engine]] volume. │
   └────────────────────────────┬────────────────────────────┘
                                │
                                ▼
   ┌─────────────────────────────────────────────────────────┐
   │ 2. Trade Compilation                                    │
   │    - Instantiates immutable TradeExecution struct.      │
   │    - Records source Order IDs & high-precision time.    │
   └────────────────────────────┬────────────────────────────┘
                                │
                                ▼
   ┌─────────────────────────────────────────────────────────┐
   │ 3. Egress Serialization ([[concepts/kafka-integration]])│
   │    - Marshaled to JSON payload.                         │
   │    - Sharded by Symbol to 'nte.trades.matched'.         │
   └────────────────────────────┬────────────────────────────┘
                                │
                  ┌─────────────┴─────────────┐
                  ▼                           ▼
     ┌──────────────────────────┐┌──────────────────────────┐
     │ [[entities/trade-settlement-system]] ││ [[entities/compliance-surveillance-monitor]] │
     │ - Performs settlement    ││ - Scans for wash trading│
     │ - Modifies user balance  ││ - Inspects account IDs  │
     └──────────────────────────┘└──────────────────────────┘
```

### 1. Generation Phase
The lifecycle begins in the [[entities/order-book]]. When an inbound limit or market order is evaluated against resting liquidity, the matching loops execute. If a match is made, a `TradeExecution` is generated. If an [[concepts/iceberg-order-engine]] is involved, the transaction's quantity is bound by the visible `DisplayQuantity` slice rather than the total parent volume, triggering replenishment routines immediately after compilation.

### 2. Dispersal Phase
Once returned to the parent `Engine` registry, the record is evaluated alongside engine metrics (recording the microsecond elapsed-time metrics) and dispatched to `events.KafkaPublisher`. 

As configured in [[decisions/configuration-latency-tuning]], the egress layer operates with `producer_acks: "all"` and `linger_ms: 1`. This trade-off prioritizes durability and immediate downstream notification over bulk serialization throughput, guaranteeing that no executed trade is acknowledged to clients without a durable, immutable ledger entry in the Kafka cluster.

### 3. Consumption Phase
The trade record is concurrently consumed by:
* The **[[entities/trade-settlement-system]]**, which parses account balances for the buyer and seller to initiate asynchronous transfer of funds and custody updates.
* The **[[entities/compliance-surveillance-monitor]]**, which cross-references the matching `buyer_id` and `seller_id` against account registration indices to flag self-matching execution patterns or potential manipulative behavior.
