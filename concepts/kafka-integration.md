# Kafka Integration & Egress Pipeline

The egress pipeline of the **Nexus Trading Exchange (NTE) Order Matching Engine (OME)** is built upon a high-performance, low-latency wrapper around `librdkafka` (via the Confluent Kafka Go client). This integration serves as the unified event-streaming pipeline, decoupling the stateful, in-memory [[entities/matching-engine]] core from downstream execution systems.

By streaming serialized events onto deterministic Kafka logs, the OME feeds real-time transaction records to the [[entities/trade-settlement-system]] (TSS), market depth snapshots to the [[entities/market-data-gateway]] (MDG), and operational transaction logs to the [[entities/compliance-surveillance-monitor]] (CSM).

---

## 1. Architectural Role & Flow Control

The egress pipeline receives execution records generated by individual [[entities/order-book]] instances and publishes them asynchronously to prevent network I/O from blocking the critical matching loop. 

```
┌──────────────────────────────────────────────────────────┐
│              Deterministic Matching Core                 │
│               (Isolated Order Books)                     │
└──────────────────────────┬───────────────────────────────┘
                           │ 
                           │ Generates:
                           │ - []models.TradeExecution
                           │ - OrderBook Snapshot Data
                           ▼
┌──────────────────────────────────────────────────────────┐
│              Egress Layer: KafkaPublisher                │
│                                                          │
│  ┌──────────────────────┐      ┌──────────────────────┐  │
│  │ Low-Latency JSON     │      │ Symbol-Keyed         │  │
│  │ Serialization        │      │ Partitioning Router  │  │
│  └──────────┬───────────┘      └──────────┬───────────┘  │
└─────────────┼─────────────────────────────┼──────────────┘
              │                             │
              ▼                             ▼
┌───────────────────────────────────────────┬──────────────┐
│  librdkafka C-Underlay Buffer              │              │
├───────────────────────────────────────────┼──────────────┤
│  linger.ms=1                              │ acks=all     │
└─────────────┬─────────────────────────────┴──────┬───────┘
              │                                    │
              ▼ (TCP Stream)                       ▼ (TCP Stream)
┌──────────────────────────────┐     ┌─────────────────────────────┐
│ Topic: nte.trades.matched    │     │ Topic: nte.orderbook.snapshots
├──────────────────────────────┤     ├─────────────────────────────┤
│ - Consumed by TSS & CSM      │     │ - Partitioned by Symbol     │
│ - Zero-loss guarantee        │     │ - Consumed by MDG           │
└──────────────────────────────┘     └─────────────────────────────┘
```

The matching engine enforces a strict separation of concerns using the [[decisions/split-locking-pattern]]. Once an order is matched, control is quickly handed over to the `KafkaPublisher` to push events to Kafka topics, ensuring that thread contention within individual order books is kept to an absolute minimum.

## 2. Low-Latency JSON Serialization

While binary protocols (like SBE or Protobuf) offer marginal serialization advantages, NTE implements heavily optimized, structurally aligned JSON schemas to balance cross-organizational compatibility, human readability for compliance audits, and ingestion speeds.

### Serialization Strategy & Optimizations
1. **Struct Alignment and Pre-allocation:** In-memory slices are pre-allocated at the matching boundary before serialization.
2. **Standard Library Alternatives:** To avoid Go's reflection-heavy standard library `encoding/json` overhead during high-concurrency periods, the production setup is configured to support code-generated serializers (such as `easyjson`) or direct byte-buffer serialization.
3. **Avoidance of Pointer Indirection:** Struct fields in [[entities/trade-execution-model]] and [[entities/order-model]] are kept flat to ensure the compiler can optimize stack allocation and minimize Garbage Collector (GC) pressure.

### Data Models Configured for Egress
The primary structures serialized and pushed over the wire include:

#### Trade Execution Schema (`models.TradeExecution`)
Consumed by the [[entities/trade-settlement-system]] for clearing and custody updates, and by the [[entities/compliance-surveillance-monitor]] for wash-trading and spoofing analysis.

## 3. Symbol-Keyed Partitioning

A critical requirement of any financial matching engine is maintaining the absolute temporal sequence of transactions *per instrument*. While trades across different symbols (e.g., `BTC/USD` and `ETH/USD`) can execute concurrently without coordination, trades within `BTC/USD` must be processed chronologically downstream.

To achieve this, the OME utilizes **Symbol-Keyed Partitioning**:

*   **Partition Routing Rule:** The Kafka broker partition is selected using the hash of the message `Key`. By assigning the instrument symbol (e.g., `BTC/USD`) as the key of the message payload, all events related to that symbol are consistently routed to the same physical Kafka partition.
*   **Downstream FIFO Enforceability:** Because Kafka guarantees order execution *within a single partition*, downstream consumers (such as the [[entities/market-data-gateway]] reconstructing L2/L3 order books) can consume from a partition knowing that the messages are ordered exactly as they were executed in memory.
*   **State Replay Integrity:** During a system recovery event (see [[concepts/crash-recovery-durability]]), the engine replays inbound logs sequentially. Symbol partitioning allows the matching engine to parallelize replay tasks by dedicating distinct worker threads to individual partition logs.

## 4. Configuration Profiles using librdkafka

The underlying performance of the `events.KafkaPublisher` is determined by configuration tuning parameters specified in `config/exchange.yaml`. Under the hood, these values are parsed and applied directly to the C-based `librdkafka` library.

### Configuration Specification (`config/exchange.yaml`)
```yaml
exchange:
  id: "NTE-PROD-01"
  region: "ny4"

matching:
  algorithm: "PRICE_TIME_PRIORITY"

kafka:
  brokers: "kafka-cluster.nte.gfmg.internal:9092"
  topics:
    inbound_orders: "nte.orders.inbound"
    matched_trades: "nte.trades.matched"
    snapshots: "nte.orderbook.snapshots"
    rejected_orders: "nte.orders.rejected"
  producer_acks: "all"
  linger_ms: 1
```

### Key Performance Profiles Explained

For a deeper dive into how these configurations affect queue mechanics, review [[decisions/configuration-latency-tuning]].

#### `producer_acks = "all"` (acks=-1)
This setting requires the leader broker to wait for a full acknowledgment from the complete set of in-sync replicas (ISRs) before confirming receipt of the write. This is a non-negotiable setting for financial safety:
*   Guarantees that no matched trade is lost due to a broker crash.
*   Ensures that both the in-memory states and the committed log records remain perfectly in sync, which is vital for [[concepts/crash-recovery-durability]].

#### `linger.ms = 1`
Dictates the maximum time the producer will wait for other messages to arrive before sending a batch. 
*   In standard corporate messaging, this value is often set to `20-100ms` to optimize throughput.
*   For the NTE OME, this is limited to `1ms` (or `0` in ultra-low-latency environments). A `1ms` window allows the low-latency thread to aggregate rapid bursts of microsecond-level matches into single physical TCP payloads, reducing system call overhead while keeping latency overhead practically invisible.

## 5. Technical Implementation: `KafkaPublisher`

The following structure implements the publisher interface using Go bindings for `librdkafka`.

```go
package events

import (
	"encoding/json"

	"github.com/Astrophage/order-matching-engine/models"
	"github.com/confluentinc/confluent-kafka-go/v2/kafka"
	"github.com/sirupsen/logrus"
)

type KafkaPublisher struct {
	producer      *kafka.Producer
	tradeTopic    string
	snapshotTopic string
	log           *logrus.Logger
}

func NewKafkaPublisher(brokers, tradeTopic, snapshotTopic string, log *logrus.Logger) (*KafkaPublisher, error) {
	// Map YAML parameters directly to librdkafka configuration parameters
	p, err := kafka.NewProducer(&kafka.ConfigMap{
		"bootstrap.servers":  brokers,
		"acks":               "all",  // Guarantee persistent durability
		"linger.ms":          1,      // Minimize latency while allowing micro-batching
		"compression.type":   "none", // Disable compression to reduce CPU serialization latency
		"socket.nagle.disable": true, // Disable Nagle's algorithm for immediate TCP transmission
	})
	if err != nil {
		return nil, err
	}
	return &KafkaPublisher{
		producer:      p,
		tradeTopic:    tradeTopic,
		snapshotTopic: snapshotTopic,
		log:           log,
	}, nil
}

// PublishTrades broadcasts executed matches to 'nte.trades.matched'
// These are consumed by the TSS and CSM
func (kp *KafkaPublisher) PublishTrades(trades []models.TradeExecution) {
	for _, t := range trades {
		payload, err := json.Marshal(t)
		if err != nil {
			kp.log.Errorf("Failed to marshal trade: %v", err)
			continue
		}

		// Trades do not use strict symbol keying for clearing; they are handled in round-robin fashion
		// across trade settlement consumers unless specific routing keys are mandated.
		err = kp.producer.Produce(&kafka.Message{
			TopicPartition: kafka.TopicPartition{Topic: &kp.tradeTopic, Partition: kafka.PartitionAny},
			Value:          payload,
		}, nil)
		
		if err != nil {
			kp.log.Errorf("Kafka local queue error: %v", err)
		}
	}
}

// PublishSnapshot sends L2/L3 book snapshots to 'nte.orderbook.snapshots'
// These are consumed by the Market Data Gateway and must be symbol-keyed
func (kp *KafkaPublisher) PublishSnapshot(symbol string, snapshot interface{}) {
	payload, err := json.Marshal(snapshot)
	if err != nil {
		kp.log.Errorf("Failed to marshal snapshot: %v", err)
		return
	}

	// KEY CONSTRAINT: Using symbol as Key to guarantee deterministic partition routing.
	// This ensures that all updates for "BTC/USD" land on the same partition.
	err = kp.producer.Produce(&kafka.Message{
		TopicPartition: kafka.TopicPartition{Topic: &kp.snapshotTopic, Partition: kafka.PartitionAny},
		Value:          payload,
		Key:            []byte(symbol), 
	}, nil)

	if err != nil {
		kp.log.Errorf("Failed to queue snapshot: %v", err)
	}
}
```

### Error Handling & Fallback Modes
If connection to the Kafka cluster fails or breaks during operation:
1.  **Local Buffering:** `librdkafka` holds messages in its internal C-memory queue up to `queue.buffering.max.messages`.
2.  **Fallback Warning Mode:** If the connection cannot be initialized upon startup, the system logs a high-severity alert and runs in fallback mode (useful for local development or sandbox simulations).
3.  **Backpressure & Circuit Breaking:** If the outbound producer queue becomes full (signaled by a `Local: Queue full` error), the engine will apply backpressure to the ingress layer, eventually rejecting new inbound orders via the `nte.orders.rejected` flow to protect in-memory state consistency.
